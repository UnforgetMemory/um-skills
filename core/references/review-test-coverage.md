# 必需测试覆盖评估

## 流程

1. 从变更清单列出每一个行为变更
2. 对每个变更评估：现有测试覆盖了吗？缺什么？

## 最低覆盖标准（每个行为变更）

- **快乐路径**：有效输入 → 预期结果
- **边界**：空 / 最大长度 / 0 / null / 并发
- **错误路径**：无效输入 → 明确错误（类型 + 消息）
- **回归**：修复型变更必须有"先复现失败"的测试

## 测试先行纪律（TDD）

1. **RED**：写一个失败的测试，运行它，记录断言错误（证明失败的原因正确——而非语法/导入错误）
2. **GREEN**：最小实现使其通过，记录通过输出
3. **SURFACE**：真实表层验证（真实 HTTP 请求 / CLI / 浏览器运行）
4. **REGRESSION**：重跑完整套件，确认全部通过

## 测试质量检查

- [ ] 测试断言行为（输出/状态），而非实现细节
- [ ] 测试名称描述行为（`returns 400 for invalid email`，而非 `test2`）
- [ ] 无仅快乐路径的缺口
- [ ] 测试可维护（无基于 sleep 的竞态、无超时陷阱）

## 套件运行

- 运行项目实际测试套件（无论项目用什么 runner）
- 全部通过 → 门禁通过
- 既有失败单独列出，标注"非本次变更引入"——绝不混入本次变更的结果

## 报告

```
behavior change → existing covering test(id) → missing cases → new test(id) → RED→GREEN evidence path
```
