## 人工确认协议（commit / push / release）

适用范围：任何 `git commit` / `git push` / `git tag` / `gh release create` 及等价发布动作。违反协议 = 严重违规，Review 必须拦截。

1. **内容先展示**：执行前必须向用户完整展示——commit（变更清单 + 提交计划 + 完整提交消息）、push（目标远程/分支 + 待推 commit 集）、release/tag（版本号 + Notes 全文 + 发布形态）。
2. **确认机制**：确认必须经交互工具面板（一次多问，见 `decision-panel.md`）；各环境通道：dsh = `ask_user_question`，opencode / codex = 文本编号选项。**选项未返回 = 未确认 = 禁止执行**。
3. **单次效力（仅本次默认）**：「仅本次」确认只覆盖「当次展示的具体内容 + 当次执行」；执行完成、内容任何变更、或进入新一轮后，该确认即失效，必须重新展示并重新确认。「本会话允许」不受本条限制（见 #4），但每次执行前仍须重新展示内容。
4. **会话级允许（可选豁免）**：确认面板必须提供效力选项——「仅本次」（默认推荐）与「本会话允许」；本会话允许仅豁免同动作类型的逐次面板**确认项**（后续轮出现新的非确认决策如版本升级时，仍须提出该决策项，一次交互），**内容展示永不豁免**；授权范围以用户选择该选项当轮的面板选项为准（如 umrelease Q2 的发布范围），后续轮沿用该范围，禁止自动扩大；授权仅限用户显式选择该选项，禁止 agent 推定、禁止把「仅本次」自动升级为「本会话允许」；授权仅本会话有效（会话结束即失效），用户可随时撤销（声明即回到仅本次），禁止写入长久记忆或指令文本，新会话重新确认。
5. **禁止推定**：任务描述或历史对话中出现「提交/推送/发布」字眼 ≠ 对本轮具体内容的确认；内容未展示或面板未返回 → 禁止执行，不得以「用户已要求」代替。
6. **平台审批非替代品**：平台审批弹窗不是确认通道的替代；审批被禁用（如 dsh policy=never）时，面板确认依然是唯一且必须的确认通道。
7. **条件执行**：面板「依赖决策」项（如「提交后推送」）在依赖失败时必须暂停回报，未经再次确认禁止自动重试。
8. **证据记录**：确认结果（面板编号 + 用户选项 + 效力层级）写入分册报告「人工确认记录」行；无记录 = 无确认 = 违规。

## 前置安全门禁（任何修改/删除操作之前）

任何修改/创建/删除之前，所有门禁必须通过。未满足时，该操作被禁止，直到用户明确允许。

### 门禁表

| # | 门禁条件 | 未满足时 |
|---|----------------|----------|
| A | 唯一识别 root project 且操作目标在其工作区内（见下「root 识别」；部署/同步副本误判排查见门禁 E 决策流第 1 步） | 阻止操作；识别不出 → 提问用户，禁止乱操作 |
| B | Git 仓库配置了远程（`git remote`） | 阻止修改/删除；报告缺少远程；等待 |
| C | 已配置 Git 身份（`user.name` / `user.email`） | 阻止修改/删除；报告缺少身份；等待 |
| D | 版本管理强制：除读取外的一切操作作用于 root 工作区（git 跟踪体系内） | 无版本管理 → 提问用户并警告；仅用户明确允许后继续 |
| E | 操作目标不在任何版本管理（git/svn/hg）内 | 禁止自动修改：报告「无版本保护」→ 等待用户方案决定；用户决定继续 → 追加备份决策（直接改 / 临时本地备份），选定前不动手 |

### root 识别（嵌套 git 判定）

1. 从操作目标路径取最近 git 根：`git -C <target> rev-parse --show-toplevel`（目标为文件 → 取其父目录）。
2. 从该根向上逐级检查父目录是否还有 `.git`/仓库边界：`git -C <parent> rev-parse --show-toplevel` 返回不同根 → 存在外层嵌套仓库；命令失败 → 无外层仓库，停止上溯。
3. 候选根唯一 → 即 root project；多个候选 → 按 `.um.agents` 项目记忆 / 询问用户确定；**识别不出或无法精确 → 提问用户，禁止乱操作**。
4. 操作目标超出 root 工作区（`--show-toplevel` 边界外）→ 走 OOB 流程（见 destructive-ops-gates.md）。

门禁顺序：A（root 识别 + 工作区边界）→ D（版本管理）→ B/C（remote/身份）→ E（无版本保护目标，见下）。任一门禁失败 → 询问用户"是否继续？"并仅在明确许可后继续。

### 门禁 E 决策流（无版本保护目标）
1. 判定前先排误判：目标可能是某仓库的部署/同步副本（同内容源仓库、deploy 脚本、批量部署时间戳）→ 修改落到源仓库再同步副本，禁止直接改副本
2. 确认目标确无版本保护 → 停止自动修改，报告（目标路径 + 无 git/svn/hg 证据），等待用户方案决定；此前的修改意图/授权 ≠ 本轮授权，必须等本轮明确答复
3. 用户决定继续 → 追加二选一提问：直接修改 / 先建临时本地备份（`<file>.bak` 或临时目录副本）；选定后才执行
4. 完成后回报：改动内容 + 备份位置（如有）
