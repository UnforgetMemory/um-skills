# 代码评审清单 —— 五个轴

## 严重度标签

| 前缀 | 含义 | 处置 |
|--------|---------|----------|
| **Critical:** | 阻止合并 | 安全漏洞 / 数据丢失 / 功能损坏 |
| *（无前缀）* | 必须修复 | 合并前必须解决 |
| **Nit:** | 可选 | 格式、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑，非必须 |
| **FYI** | 仅供参考 | 无需行动 |

## 五轴评审

### 1. Correctness（正确性）
- [ ] 符合规格 / 任务要求
- [ ] 边界情况（null / 空 / 边界值）
- [ ] 错误路径已处理（不只是快乐路径）
- [ ] 竞态 / off-by-one / 状态不一致
- [ ] 测试断言行为，而非实现细节

### 2. Readability & Simplicity（可读性与简洁性）
- [ ] 命名清晰一致（禁止无上下文的 `temp` / `data` / `result`）
- [ ] 控制流直接（简化嵌套三元、深层回调）
- [ ] 行数合理（本应 100 行却写 1000 行 = 失败）
- [ ] 抽象有依据（仅在第三次使用时才泛化）
- [ ] 无死代码（空操作变量、兼容 shim、`// removed` 注释）

### 3. Architecture（架构）
- [ ] 遵循既有模式；新模式有依据（抽象来自真实变更）
- [ ] 模块边界干净
- [ ] 无重复代码
- [ ] 依赖方向正确（无循环依赖）

### 4. Security（安全）
- [ ] 用户输入在边界校验
- [ ] 代码 / 日志 / 版本控制中无密钥
- [ ] AuthN/AuthZ 检查到位
- [ ] SQL 参数化
- [ ] 输出针对 XSS 编码
- [ ] 外部数据源视为不可信

### 5. Performance（性能）
- [ ] 无 N+1 查询
- [ ] 无无界循环 / 无约束数据拉取
- [ ] 该异步处同步 → 异步
- [ ] 列表端点分页
- [ ] 热路径上无大对象

## 变更规模

```
~100 lines  → good, reviewable in one pass
~300 lines  → acceptable (single logical change)
~1000 lines → too large, propose splitting
```

重构 vs 功能：本会话只**建议**拆分方案；不执行提交。

## 评审流程

1. **理解意图**：该变更解决什么问题？对应哪份规格？
2. **先审测试**：测试存在吗？测试行为吗？覆盖边界吗？能抓住回归吗？
3. **按五个轴逐文件走查**
4. **为每条发现标注严重度**
5. **验证证据链**：测试 / 构建 / 手工验证证据是否完整？

## 信条

> 评审的职责不是证明代码能工作——而是证明代码会在哪里失败。始终追猎失败路径，而非快乐路径确认。

## 输出格式

```
[severity] <file>:<line> — <issue> — <suggested fix>
```
