# Code Review 清单（五轴）

调用 skill：`code-review-and-quality`（完整规范以该 skill 为准，本文档为执行清单）

## 严重度标签

| 前缀 | 含义 | 处理 |
|---|---|---|
| **Critical:** | 阻断合并 | 安全漏洞 / 数据丢失 / 功能破坏 |
| *(无前缀)* | 必须修改 | 合并前必须处理 |
| **Nit:** | 可选 | 格式、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑但不必须 |
| **FYI** | 信息 | 无需动作 |

## 五轴审查

### 1. Correctness

- [ ] 符合规格/任务要求
- [ ] 边界情况（null / empty / 边界值）
- [ ] 错误路径处理（不止 happy path）
- [ ] 竞态 / off-by-one / 状态不一致
- [ ] 测试测的是行为而非实现细节

### 2. Readability & Simplicity

- [ ] 命名清晰一致（禁止无上下文的 `temp` / `data` / `result`）
- [ ] 控制流直接（嵌套三元、深回调 → 简化）
- [ ] 行数精简（1000 行能 100 行完成 = 失败）
- [ ] 抽象配得上复杂度（第三次使用才泛化）
- [ ] 无死代码（no-op 变量、兼容 shim、`// removed` 注释）

### 3. Architecture

- [ ] 遵循既有模式；新模式是否合理（引用 umpp 的 Evolution First：抽象来自真实变化）
- [ ] 模块边界干净
- [ ] 无重复代码
- [ ] 依赖方向正确（无循环依赖）

### 4. Security

- [ ] 用户输入在边界校验
- [ ] 无密钥进代码/日志/版本控制
- [ ] 鉴权/授权检查到位
- [ ] SQL 参数化
- [ ] 输出编码防 XSS
- [ ] 外部数据源视为不可信
- 详细：`security-and-hardening` / [security-audit.md](security-audit.md)

### 5. Performance

- [ ] 无 N+1
- [ ] 无无界循环 / 无约束数据拉取
- [ ] 同步操作改为异步的必要性
- [ ] 列表端点分页
- [ ] 热路径无大对象

## 变更尺寸

```
~100 行   → 良好，一次可审完
~300 行   → 可接受（单一逻辑变更）
~1000 行  → 过大，建议拆分
```

重构与功能分离：本次会话内仅**建议**拆分方案，不执行提交。

## 审查流程

1. **理解意图**：该变更解决什么问题？对应什么规格？
2. **先审测试**：测试存在？测行为？边界覆盖？能捕获回归？
3. **逐文件走查五轴**：每个变更文件过一遍五轴清单
4. **标注严重度**：每条发现必须带标签
5. **核实验证故事**：测试/构建/手动验证的证据是否齐全

## 信条

> Review 的职责不是证明代码可以工作，而是尽可能证明代码会在什么地方失败。
> 始终以寻找失败路径（Failure Path）代替确认成功路径（Happy Path）作为第一思维方式。

## 输出格式

```
[严重度] <文件>:<行> — <问题> — <建议修复>
```
